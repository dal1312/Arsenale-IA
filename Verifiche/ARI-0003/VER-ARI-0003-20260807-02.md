# VER-ARI-0003-20260807-02 — Diagnosi indipendente del release gate Redis di Omega FL

- **Identificativo:** VER-ARI-0003-20260807-02
- **Procedura:** ARI-0003
- **Versione procedura:** 0.2.0
- **Data:** 2026-08-07
- **Progetto:** dal1312/ciuccio-omega-fl
- **Revisione:** fa4ea2c873b1aa07a110f10a90a23557bba4470d
- **Tipo prova:** Indipendente
- **Stato evidenza:** Valida

## Ambito

Diagnosticare il fallimento del release gate RC3 che ha portato alla PR #34 `ci: provision Redis for full release validation`. Il sintomo registrato dalla PR è che `validate_local.py` non riusciva a raggiungere Redis su `localhost:6379` durante la validazione completa in GitHub Actions. La prova verifica il percorso causale nel codice pre-fix e la regressione post-fix senza attribuire cause non supportate ai log storici non più disponibili.

## Ambiente e accesso

Accesso in lettura al commit pre-fix `fa4ea2c873b1aa07a110f10a90a23557bba4470d`, alla PR #34, al diff del fix e ai risultati del release gate sul merge commit `c5987ba0e33e80394db249dd1f0c1fb128172f44`. Il dettaglio testuale della failure originale non è più disponibile tramite i log interrogati; il sintomo è però registrato nel corpo della PR ed è coerente con il percorso di codice pre-fix.

## Passi esercitati

1. Registrato il comportamento atteso: la validazione completa del release gate deve eseguire i controlli runtime e completarsi senza dipendere da un servizio non predisposto.
2. Registrato il comportamento reale dichiarato: `validate_local.py` fallisce perché Redis non è raggiungibile su `localhost:6379`.
3. Ridotto il problema al percorso `generate_release_reports.py --full` → `validate_local.py` → `assert_redis_reachable()`.
4. Separate le ipotesi: errore del test applicativo, configurazione host/porta errata, Redis richiesto ma non provisionato, oppure problema Docker generale.
5. Verificato il codice pre-fix e il requisito di connettività.
6. Identificata la causa radice operativa: la validazione completa richiede Redis, mentre il percorso GitHub Actions non garantiva che il servizio fosse disponibile prima dell'invocazione.
7. Verificata la correzione della PR #34: Redis temporaneo gestito soltanto in GitHub Actions quando il PING fallisce, attesa readiness e cleanup.
8. Verificata la regressione tramite test aggiunto e soprattutto tramite release gate reale post-merge.

## Verifiche osservabili

- La PR #34 dichiara esplicitamente: `validate_local.py` non poteva raggiungere Redis su `localhost:6379` durante il release gate RC3.
- Nel commit pre-fix, `generate_release_reports.py` con `full=True` aggiunge il controllo `local-runtime-security-validation` eseguendo `scripts/validate_local.py`.
- Nello stesso commit, `validate_local.py` imposta `ROUND_STORE_HOST=localhost` e `ROUND_STORE_PORT=6379` quando non sono già valorizzati.
- `assert_redis_reachable()` tenta una connessione TCP al servizio e, su `OSError`, stampa `Redis preflight failed`, suggerisce di avviare Redis e termina con `SystemExit(1)`.
- Il fallimento avviene quindi prima della lunga suite di compile, configurazione, database, backup/restore e pytest.
- La patch #34 aggiunge un PING Redis reale, avvia un container Redis 7 etichettato solo quando necessario in GitHub Actions, attende readiness e lo rimuove in `finally`.
- Il release gate post-merge `29382236320` sul commit `c5987ba0e33e80394db249dd1f0c1fb128172f44` è `success`; risultano riusciti validazione completa, packaging, provenance, install check, Docker E2E e cleanup.
- Il test aggiunto dalla PR fornisce una regressione strutturale; una review successiva ARI-0002 ha correttamente classificato la sua copertura comportamentale come migliorabile, senza invalidare la prova end-to-end del fix.

## Rilievi prodotti

### OFL-DIAG-001 — Causa radice confermata con limite storico sui log

- **Sintomo:** release gate RC3 incapace di completare la validazione runtime perché Redis locale non era raggiungibile.
- **Causa radice:** dipendenza runtime obbligatoria di `validate_local.py` non provisionata dal percorso GitHub Actions prima della validazione completa.
- **Correzione minima:** predisporre Redis temporaneo solo nel contesto CI e solo se il servizio non risponde già, senza cambiare API, dipendenze o versione prodotto.
- **Regressione:** test aggiunto e release gate reale post-merge verde.
- **Esito:** il percorso completo di release supera i controlli dopo il fix.

## Limiti

- Il log dettagliato della failure originale non è più disponibile tramite l'endpoint interrogato; la formulazione del sintomo proviene dalla PR e la causa è verificata sul codice pre-fix.
- Una run pre-fix recuperata sul commit base risulta cancellata durante controlli precedenti e non costituisce prova utile della failure Redis; non viene quindi usata come evidenza causale.
- Il test di regressione della PR è prevalentemente strutturale; il release gate post-merge fornisce la prova comportamentale positiva più forte.

**RISOLTO CON COPERTURA DA RAFFORZARE.** La causa operativa è eliminata e il release gate reale completa con successo il percorso che prima richiedeva Redis non disponibile. Resta consigliato migliorare i test unitari dei rami negativi, rilievo già separato dalla diagnosi funzionale.
