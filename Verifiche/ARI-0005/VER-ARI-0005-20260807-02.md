## Ambito

Valutare come applicazione reale di ARI-0005 la PR #34 `ci: provision Redis for full release validation`. Il requisito era correggere il release gate RC3, che richiedeva Redis durante la validazione completa senza garantirne la disponibilità, mantenendo invariati API, dipendenze e versione prodotto e introducendo gestione CI limitata al caso necessario.

## Passi esercitati

1. Confermato l'ambito dichiarato nella PR: provisioning Redis soltanto per la full validation in GitHub Actions.
2. Verificata la causa già diagnosticata: il percorso `generate_release_reports.py --full` invoca `validate_local.py`, che richiede Redis raggiungibile.
3. Esaminato il più piccolo incremento funzionale: ping, start, readiness e stop di un Redis temporaneo.
4. Verificata la guardia su GitHub Actions, host locale e porta valida per evitare ampliamento del comportamento normale.
5. Verificato il test di regressione aggiunto.
6. Verificato il cleanup in `finally`.
7. Verificato il release gate reale sul merge commit.
8. Controllato che la PR non modifichi API, dipendenze o versione prodotto come dichiarato.

## Verifiche osservabili

- `_redis_ping()` prova il servizio effettivo invece di assumere la disponibilità della porta.
- `_start_ci_validation_redis()` è un no-op fuori da GitHub Actions o quando host/porta non corrispondono al contesto locale previsto.
- Se Redis risponde già, non viene avviato un container aggiuntivo.
- Il container temporaneo usa nome legato a run/attempt, label dedicata, bind `127.0.0.1` e readiness loop.
- `_stop_ci_validation_redis()` viene eseguito in `finally` dopo `generate_reports()`.
- È stato aggiunto un test di regressione nel repository.
- Il release gate post-merge `29382236320` è verde, inclusi validazione completa, packaging, provenance, install check, Docker E2E e cleanup.
- Una successiva code review ARI-0002 ha classificato come **Media** la qualità del test perché prevalentemente basato sul testo del sorgente; il rilievo non invalida il comportamento end-to-end del fix.
